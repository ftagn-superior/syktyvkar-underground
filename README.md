# Syktyvkar Underground

Небольшая браузерная сетевая технодемо: одна площадка с двумя домами, до восьми игроков, столкновения и один общий физический ящик. Собственный персонаж реагирует с локальным предсказанием; сервер рассчитывает общий мир. Основа — **Babylon.js + Havok + Colyseus, TypeScript и Vite**.

## Локальный запуск

Нужен **Node.js 24 или новее**; проверенное окружение записано в `.node-version`. Все команды выполняются из корня репозитория. Глобальная установка pnpm не обязательна:

```sh
npx --yes pnpm@12.18.0 install --frozen-lockfile
npx --yes pnpm@12.18.0 dev
```

Откройте **http://127.0.0.1:5173** и нажмите «Войти». Для второго игрока откройте этот же адрес в новой вкладке или другом браузере. Если pnpm 12.18.0 уже установлен, можно использовать обычные `pnpm install --frozen-lockfile` и `pnpm dev`.

- **WASD / стрелки** — движение относительно экрана; подойдите к ящику, чтобы толкнуть его.
- **Q / E** или кнопки **↶ / ↷** — плавный поворот камеры на 90°. Управление учитывает текущий ракурс. Стены, крыши и детали домов, закрывающих вашего персонажа, автоматически становятся полупрозрачными; столкновения сохраняются.
- **На старт** — безопасное возвращение своего персонажа. Кнопка показывает ожидание подтверждения сервера, затем отсчитывает три секунды до следующего возврата.
- **Выйти** — сразу освободить место. При закрытии или обновлении вкладки сессия сохраняется на 30 секунд; повторный вход в той же вкладке восстанавливает персонажа.
- Кнопка **Диагностика** открывает показатели соединения, кадров и коррекций.
- `Ctrl+C` в консоли останавливает оба процесса. После перезапуска сервера мир начинает заново.

Целевой браузер — настольный Chromium/Chrome с WebGL2 и клавиатурой. Работающие приложения не загружают движок, WASM, шрифты или другие ресурсы с внешних CDN. Интернет нужен для первоначальной установки зависимостей.

В панели диагностики можно выбрать качество **«Обычное»** или **«Экономное»**. Экономный режим отключает тени и уменьшает ширину и высоту внутреннего изображения до ⅔ обычного; выбор сохраняется в браузере. После смены качества измерения кадров начинаются заново с 60-секундного прогрева видимой игры. **«Скачать отчёт»** сохраняет JSON со сведениями о сборке, версиях мира и протокола, окне браузера, качестве графики, кадрах и соединении.

При потере графического контекста управление останавливается и появляется постоянное сообщение. После автоматического восстановления графики можно продолжить новым нажатием клавиши. Если восстановление не происходит, в сообщении доступна кнопка перезагрузки страницы.

`pnpm dev` собирает данные мира и запускает Vite на порту **5173**, сервер — на **2567**. Освободите эти порты, если они заняты. Изменения TypeScript подхватываются автоматически; после изменения JSON-сцены перезапустите команду. По умолчанию оба процесса доступны только с текущего компьютера.

## Собранная версия

```sh
npx --yes pnpm@12.18.0 build
npx --yes pnpm@12.18.0 start
```

Откройте **http://127.0.0.1:2567**. Один Node.js-процесс обслуживает клиент, данные мира и WebSocket. Сборка находится в `dist/`, включая локальную копию Havok WASM. Запускать `start` нужно из корня репозитория; после изменений исходников повторите `build`. Docker, база данных, CI и публикация для локальной работы не нужны.

## Выбор мира

По умолчанию сборка и сервер используют малый `physics-lab`. Для синтетической карты 2 × 2 км:

```sh
SU_WORLD_SOURCE=content/worlds/streaming-lab/world.json pnpm build
SU_WORLD_DIRECTORY=dist/worlds/streaming-lab pnpm start
# Для Vite и сервера разработки:
SU_WORLD_SOURCE=content/worlds/streaming-lab/world.json SU_WORLD_DIRECTORY=dist/worlds/streaming-lab pnpm dev
```

Сервер обслуживает один выбранный мир. `streaming-lab` содержит 1600 домов, 256 ячеек и плиток земли;
данные генерируются при сборке из фиксированного seed. С L3 браузер загружает заголовок и WASM, а после присоединения — только область подготовки,
выбранную сервером. Возврат и переподключение готовят целевую область перед возобновлением движения. Пакет и сервер уже используют формат мира 3 и протокол 3.
Сервер отправляет только ближайших игроков и ящик: добавить при ≤80 м, убрать при >100 м. Собственный игрок и общая занятость не фильтруются; отсутствие ящика не блокирует управление. Старые клиенты получают несовместимость версии. Подробнее — в [инструкции карты](docs/building-assets.md).

## Ручной запуск через meta.ftagn.xyz

На сервере `ftagn.xyz` Caddy направляет **https://meta.ftagn.xyz** на **127.0.0.1:2567**. Используется собранная версия: один процесс обслуживает страницу, API и WebSocket игры. Порт **5173** относится только к Vite в режиме `dev`; домен настроен на порт **2567**.

В консоли сервера подготовьте сборку из корня проекта (при первом запуске или после обновления исходников):

```sh
cd /root/local-repo/syktyvkar-underground
npx --yes pnpm@12.18.0 install --frozen-lockfile
npx --yes pnpm@12.18.0 build
```

Затем запускайте приложение одной командой из этого же каталога:

```sh
HOST=127.0.0.1 PORT=2567 node dist/server/main.mjs
```

Откройте **https://meta.ftagn.xyz** и нажмите «Войти». Процесс работает в текущей консоли, журналы выводятся туда же; `Ctrl+C` останавливает игру. Для работы после отключения SSH можно запускать эту команду внутри `tmux`. Пока процесс остановлен, домен возвращает **502 Bad Gateway**. При новом запуске состояние мира сбрасывается. CI, Docker, deploy и отдельный сервис приложения для этого режима не требуются.

Проверка при запущенном приложении:

```sh
curl -fsS https://meta.ftagn.xyz/health/ready
# {"ready":true}
```

Настройка домена находится на сервере в `/etc/caddy/sites/meta.ftagn.xyz.caddy`; её подключает существующий `/etc/caddy/Caddyfile`:

```caddyfile
meta.ftagn.xyz {
    encode zstd gzip
    reverse_proxy 127.0.0.1:2567
}
```

Caddy обслуживает HTTPS и перенаправляет HTTP на HTTPS. [Обычный `reverse_proxy` поддерживает WebSocket](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming), поэтому отдельные маршруты для игрового соединения не нужны. Перезапуск игры и пересборка не требуют перезагрузки Caddy. Чтобы удалить только этот домен, удалите его `.caddy`-файл, затем выполните `caddy validate --config /etc/caddy/Caddyfile && systemctl reload caddy`.

## Проверки

```sh
pnpm check
pnpm test
pnpm build
# В отдельной консоли при запущенном сервере:
pnpm load -- --clients 6 --seconds 60 --scenario crowd
```

Нагрузка использует обычный клиентский SDK и настоящие команды движения. Для восьми участников дополнительно войдите из двух браузеров. Есть сценарии `crowd` (ввод к общему ящику с периодическим отходом) и `spread` (ближайший к серверной точке появления маршрут `spread-*` из заголовка карты); `--seconds 1800` запускает 30-минутный прогон. У малого `physics-lab` нет маршрутов `spread-*`: используйте `crowd` или отдельную сборку большой карты. `--report output/validation/load.json` сохраняет JSON и создаёт каталог; `--url http://127.0.0.1:2567` задаёт сервер.

Для проверок в настоящем Chromium сначала установите тестовый браузер:

```sh
pnpm exec playwright install chromium
pnpm test:physics:browser
# После pnpm build — дома, камера и загрузка моделей со своими серверами:
pnpm test:buildings:browser
pnpm test:assets:browser
# После pnpm build — проверка перезапуска со своим сервером:
pnpm test:restart:browser
# При запущенной собранной версии на порту 2567:
pnpm test:browser
pnpm test:polish:browser
pnpm test:render:browser
pnpm test:soak
```

`test:physics:browser` запускает свой временный сервер и сравнивает Havok в Node.js и браузере. `test:browser` проверяет два независимых контекста, заполнение мира, управление и восстановление; `test:soak` выполняет 30-минутный прогон с шестью SDK-клиентами и двумя браузерами. Для двух последних нужен пустой тестовый мир. Адрес можно изменить переменной `SU_TEST_URL`, длительность прогона — `SU_SOAK_SECONDS`; путь к уже установленному Chromium — `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Браузерные сценарии сохраняют свидетельства в `output/`, который исключён из Git. Используется программный рендерер, поэтому эти сценарии проверяют поведение, а бюджет кадров нужно измерять на целевом компьютере с GPU.

`test:buildings:browser` проверяет повторное использование GLB, независимую прозрачность у двух игроков и у копий дома, поворот камеры, движение с четырёх ракурсов и сохранение столкновений. `test:assets:browser` проверяет восстановление после повреждения браузерного кэша и запрет активации персонажа при неверных ресурсах.

`test:polish:browser` проверяет обратную связь возврата, потерю фокуса и графического контекста, выбор качества, выгрузку отчёта и доступность интерфейса в небольших окнах. `test:render:browser` сравнивает режимы графики с одним неподвижным игроком при 1280 × 720: по умолчанию по 10 секунд прогрева и 15 секунд измерения на режим. Обоим нужен запущенный сервер; для сравнения графики оставьте мир без других участников. Это короткое сравнительное измерение, не аппаратная приёмка T04. Параметры `SU_PROFILE_WARMUP_MS`, `SU_PROFILE_SAMPLE_MS`, `SU_PROFILE_QUALITIES` (`standard,economy`) и `SU_PROFILE_OUTPUT` задают интервалы, режимы и путь к результату. `SU_TEST_RENDERER=hardware` убирает принудительный SwiftShader; фактически выбранный рендерер записывается в отчёт.

`pnpm test:network` отдельно запускает собственный мир для каждого профиля задержки, записывает две браузерные сессии и измеряет коррекции. Перед ним выполните `pnpm build` и `pnpm exec playwright install chromium ffmpeg`. Дополнительный `pnpm test:network:netem` проверяет потери TCP-пакетов в изолированном Linux network namespace; ему нужны `unshare`, `ip`, `tc`, `curl` и соответствующие права. Для запуска самой игры эти инструменты не требуются.

Проверки физики и контрактов лежат рядом с пакетами, сетевые — в `tests/integration`. Результаты фактических проверок и ограничения окружения записываются в `reports/`. Результат на восьми клиентах не означает готовности мира на 50 игроков.

`pnpm test:large-map:l1` собирает проект и проверяет побайтную повторяемость обоих миров, затем запускает каждый из артефакта без исходников и `node_modules`: маршруты, версии, восемь мест, отказ девятому и запрет выдачи неуказанных файлов. Свидетельства — в `output/large-map/l1/`.

`pnpm test:large-map:l4` проверяет видимость 80/100 м, движение без ящика, свежий возврат сущностей, три цикла очистки, переподключение и повороты/размеры камеры. Дополнительно измеряет выбор и кодирование восьми представлений на штатной схеме; это микрозамер состояния, не общий WS/GPU-бюджет. Результаты — в `output/large-map/l4/`.

`pnpm test:large-map:l3` собирает приложение и проверяет два браузера на большой карте через TCP relay с задержкой 100 мс и jitter ±20 мс: холодный вход, общий ящик на стыке, движение через угол, восстановление в удалённом районе, медленный HTTP/повтор и освобождение старых ячеек. Результаты — в `output/large-map/l3/`. Точки появления в этой тестовой сборке заданы серверной конфигурацией карты; браузеры двигаются обычной клавиатурой.

`pnpm test:large-map:l2` собирает отдельный пакет большой карты и проверяет в Chromium загрузку окружения 3 × 3, переходы через стыки, удержание истории, отмену/повтор запросов и освобождение ресурсов. До запуска нужен установленный Chromium. Результаты — в `output/large-map/l2/`; аппаратный бюджет кадра этим сценарием не подтверждается.

`pnpm test:large-map:l0` собирает проект и запускает технические проверки следующего этапа: StateView, добавление/удаление статики Havok в Node.js и Chromium, фиксированную сцену 2 × 2 км и исходный замер малого полигона. Серверы поднимаются автоматически; результаты сохраняются в `output/large-map/`. Прогон включает 60 секунд прогрева и 15 секунд исходного замера. Выводы и ограничения — в [отчёте L0–L5](reports/large-map.md); целевые аппаратные бюджеты и итоговая приёмка остаются L6.

Для полной автоматической проверки большой карты доступны команды со своими изолированными серверами:

```sh
pnpm test:streaming:browser  # L2–L5: ячейки, движение, ящик, AOI, отказы и сессии
pnpm test:streaming:matrix   # spread/crowd × 2/4/8, два браузера; 60 с прогрева + 60 с замера
pnpm test:streaming:netem    # Linux: RTT 200 мс ±20 мс, реальные потери TCP 1%
pnpm test:streaming:soak     # по 30 минут spread/crowd: 6 SDK + 2 Chromium
pnpm test:streaming:verify   # unit, браузерная матрица, регрессии/артефакты, нагрузка и netem
# Полная последовательность с обоими длительными прогонами:
SU_STREAMING_CHECKS=unit,browser,regression,matrix,netem,soak,supplementary pnpm test:streaming:verify
```

Каждая команда сначала собирает проект; запускайте их последовательно, чтобы пересборка не удаляла JS-файлы из-под работающего браузера. Если сборка уже готова, соответствующий `tests/streaming-*.ts` можно запустить через `node --import tsx`. Выбор отдельных проверок в `test:streaming:verify` задаётся `SU_STREAMING_CHECKS`; неизвестное имя считается ошибкой. `netem` требует `unshare`, `ip`, `tc` и разрешённых user/network namespaces; он не меняет сеть хоста. Результаты — `output/large-map/l5/`, большие JSON и журналы исключены из Git.

`test:streaming:load` запускает один профиль. Параметры: `SU_STREAMING_SCENARIO=spread|crowd`, `SU_STREAMING_CLIENTS=2|4|8`, `SU_STREAMING_SECONDS` (время замера), `SU_STREAMING_WARMUP` (прогрев), `SU_STREAMING_RTT=0|100|200`, `SU_STREAMING_OUTPUT`. Тестовые точки появления меняются только в отдельном серверном пакете мира; обычный клиент не выбирает координаты. Проверяются реальные посещённые ячейки, расстояние, 60 Гц планирования ввода, ограниченные очереди и ожидаемая AOI по авторитетному снимку. Паузы отправки при заполненной очереди записываются отдельно от частоты планирования. Отсутствие ящика не мешает движению; цель crowd известна из проверенного заголовка.

HTTP-байты ресурсов и WS-состояние/остальные WS-сообщения записываются отдельно. Клиентский отчёт содержит активные, загружаемые и удерживаемые ячейки, кэш, время подготовки, повторы, паузы и коррекции. Серверный `/api/diagnostics` разделяет физику, отбор видимости, публикацию с ACK/кодированием, работу на физический шаг и event loop. Публикация включается в цикл ближайшего завершённого шага, а не прибавляется к каждому шагу трижды. Авторитетная история для проверки AOI включена только в тестовом сервере; обычный API её не выдаёт. Выгружаемый пользовательский отчёт сохраняет агрегаты без идентификаторов живых сессий и координат игроков.

По умолчанию нагрузочные браузеры работают в SwiftShader, 960 × 640, экономном режиме. Для измерения на целевом GPU задайте `SU_STREAMING_RENDERER=default SU_STREAMING_QUALITY=standard SU_STREAMING_WIDTH=1920 SU_STREAMING_HEIGHT=1080`; фактические GL renderer/vendor сохраняются в каждом отчёте. Программный прогон и совместное размещение сервера/генераторов не закрывают аппаратные бюджеты L6.

Для итоговой приёмки на отдельном сервере можно заранее собрать тестовые пакеты с теми же точками появления, что использует автоматический стенд:

```sh
pnpm build
pnpm world:acceptance -- --scenario spread
pnpm world:acceptance -- --scenario crowd
# На целевом сервере выбирается один пакет:
HOST=0.0.0.0 SU_WORLD_DIRECTORY=output/large-map/acceptance/spread/world pnpm start
# На машине нагрузки, при двух активных браузерах на целевом GPU:
pnpm load -- --url http://SERVER:2567 --clients 6 --seconds 1860 --scenario spread --report output/validation/target-spread.json
```

Затем сервер запускается с `acceptance/crowd/world`, а нагрузка — с `--scenario crowd`. Каждый пакет содержит восемь безопасных точек и маршруты, собственные `mapVersion`/хеш симуляции; обычная сетевая схема и запрет выбора координат сохраняются. Для серверного бюджета используйте отдельный профиль 2 vCPU / 4 ГБ; первые 60 секунд отчёта — прогрев. В автоматическом стенде SDK-генераторы работают отдельным процессом; частота контролируется на каждом 60-секундном окне. Два независимых браузерных контекста работают в стандартном режиме при 1920 × 1080. Скачиваемая диагностика сохраняет текущие окна кадров/коррекций; длительный автоматический стенд дополнительно пишет периодические снимки и сырые коррекции.

После завершения всех программных прогонов `pnpm test:streaming:evidence` сверяет JSON, версии, записанные хеши исходников, длительности, реальные потери пакетов и журналы проверок. Итог — `output/large-map/l5/verification.json`; отсутствие обязательного результата или устаревшее свидетельство завершает команду ошибкой. Этот отчёт оставляет аппаратную и пользовательскую приёмку L6 открытыми.

## Устройство проекта

| Путь | Ответственность |
|---|---|
| `apps/client` | Babylon-сцена, управление, соединение, предсказание и интерфейс |
| `apps/server` | Одна Colyseus-комната, сессии, проверки команд и публикация состояния |
| `packages/contracts` | Независимые от движка типы, проверка данных и параметры протокола |
| `packages/protocol` | Сетевые схемы и преобразование снимков |
| `packages/simulation` | Общая 3D-физика, контроллер, серверный мир и мир предсказания |
| `content/worlds/physics-lab/world.json` | Препятствия, точки появления и физические параметры |
| `content/worlds/physics-lab/cells` | Экземпляры домов: устойчивые ID, ссылки на модели и размещение |
| `content/buildings` | Каталог моделей и исходники геометрии; рецепты или подготовленные GLB |
| `tools/world-build` | Проверка сцены и повторяемая сборка с хешами |
| `tools/load-test` | Активные сетевые клиенты для измерений |

Стена добавляется в JSON-сцену; масса и форма ящика также задаются данными. `pnpm world:build` выпускает согласованные артефакты клиента и сервера. Сущности имеют устойчивые ID; определение объекта, физическое состояние и визуальное представление разделены. Изменение мира применяется при перезапуске, несовместимый клиент не допускается к игре. При несовместимом изменении контрактов или общих правил движения нужно увеличить `PROTOCOL_VERSION` и пересобрать обе стороны.

Одноэтажный дом имеет основание 8 × 6 м и высоту 4,5 м, двухэтажный — 8 × 10 м и 7,5 м. Интерьеров пока нет. Мир использует формат v3 и протокол 3: визуальные GLB, коллайдеры, семантические части и размещение хранятся отдельно и связаны проверяемыми хешами. Повторяющиеся дома используют одну геометрию, сохраняя независимую прозрачность. Подготовленные сложные формы поддерживаются через составные коллайдеры и статические треугольные сетки. Как добавить модель или поставить её копию — в [инструкции по домам](docs/building-assets.md).

Предсказание использует общие правила движения и отдельный физический мир. Ящик рассчитывается сервером; в прогнозе персонажа используется приближённая форма. Прыжки, платформа, транспорт, городской импорт, аккаунты и сохранения оставлены следующим итерациям.

## Контекст и планы

Следующий согласованный этап **v0.2** — карта **2 × 2 км с лимитом 8 игроков**, загрузка окружения по ячейкам и сетевая область интереса. Сервер первой поставки сохраняет одну общую физическую симуляцию со всей упрощённой статикой; её выгрузка по участкам рассматривается после измерений. Выполнены L0–L5: пространственные данные, клиентская загрузка, сетевая видимость, нагрузочные инструменты и автоматическая матрица. Оба 30-минутных программных прогона прошли. L6 остаётся для целевых аппаратных бюджетов и пользовательской приёмки.
