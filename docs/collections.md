# Соглашения расширяемых коллекций S-29

У каждой коллекции своя предметная схема и одна каноническая инструкция. Стабильный ID не зависит от подписи или позиции в меню. Метаданные не дублируются вручную на клиенте и сервере; игровые состояния не смешиваются с авторским форматом. Общие контракты остаются без DOM, файловой системы и зависимостей от движка.

Для команд принят рисунок `<collection>:check`, `<collection>:add`, `test:<collection>`, `test:<collection>:browser`. Для реакций эти команды реализованы: [руководство](reactions.md). Для будущих команд анимаций/предметов имена закрепляются в их PR; эта страница не утверждает, что они уже существуют. Проверка проверяет весь набор и входит в обычный `pnpm check`. Добавление сначала проверяет вход и коллизии, создаёт согласованные файлы, проверяет итог и печатает дальнейшие шаги. Новые пользовательские элементы не входят побочно в PR инструментов.

## Совместимость выпусков

S-30 вводит `ContentCatalogVersions` и `matchingCatalogVersions` в `packages/contracts`. `WorldInfo.catalogVersions` и поле JOIN — карта `{ reactions: "sha256", ... }`. Сервер и клиент требуют точного совпадения набора ключей и значений; отсутствующая версия не означает совместимость. Свой ключ следующая коллекция добавляет в обе стороны. Внедрение проверки повышает протокол с 21 до 22, дальнейшее пополнение реакций само по себе не требует очередного повышения протокола: меняется отпечаток.

Сейчас S-30 формирует ключ `reactions` в `apps/server/src/index.ts` и `CLIENT_CATALOG_VERSIONS` в `apps/client/src/presentation/reaction-release.ts`. Серверная сборка проверяет байты SVG против встроенного SHA-256; браузерные URL содержат версию. Следующим PR следует **дополнить** эти карты своим ключом, сохранив `reactions`, и согласовать общий `CLIENT_CATALOG_VERSIONS` без параллельных независимых обходов допуска. Для SDK/нагрузочного клиента передавайте `catalogVersions` из `/api/world` вместе с остальными параметрами входа; такой клиент проверяет сетевую механику, а не наличие собственного визуального реестра. Браузер передаёт свою встроенную карту, а не копирует серверную.

## Порядок PR

PR S-30 самостоятелен и предназначен для `main`: нужны валидатор/генератор реакций, UI и общий допуск v22, но не реализация анимаций или предметов. Сначала интегрируйте S-30 либо перенесите его общий контракт допуска отдельным согласованным изменением; затем перебазируйте PR S-31, если он использует этот контракт. S-32 может поставлять собственные инструменты независимо, пока не меняет общую карту версий. При последующем добавлении своего ключа он следует тому же порядку. Не повышайте протокол повторно только ради второго ключа при общей поставке; изменение совместимости уже покрывается точной картой версий.

Общие места возможных конфликтов: `package.json` (объединить команды/проверки), `AGENTS.md` и `docs/README.md` (сохранить ссылки всех коллекций), `contracts/src/index.ts` и `session.ts`, серверный discovery/JOIN, клиентский preflight/recovery и документация UI. S-30 не меняет общий `ui/catalog-shortcuts.ts`, чтобы сохранять существующее поведение анимаций. Разные коллекции не обязаны иметь одинаковые эффекты, срок жизни, физику или хранение.

## Проверка и отложенные направления

Критерий обычного добавления: автор по одной инструкции получает согласованные файлы, понятные отказы и проверяемый выпуск без скрытых UI/серверных регистраций. Быстрые проверки работают с временным содержимым; сохранность прежних ID/ассетов проверяется отдельно. Сетевые/браузерные сценарии используют выделенную тестовую БД; пропуск SQL или эмуляция устройства явно отмечаются.

Внешний сервис контента, универсальный движок коллекций, виртуализация и загрузка тяжёлых ресурсов по потребности не являются зависимостями авторинга. Для них сначала нужны реальные измерения большого набора на целевом устройстве и самостоятельное решение.
