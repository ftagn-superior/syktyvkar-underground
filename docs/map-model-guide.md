# Памятка разработчика: модель карты и редактирование мира

Документ описывает модель на 12 ноября 2026 года: мир v5, ячейки v2, PostgreSQL v6 и протокол 13. В рабочей ветке добавлено ядро размещения одной скамейки во время игры. Изменение каталога, перемещение и удаление экземпляров выполняются при остановленном сервере: файловым патчем либо SQL-правками с последующей `world:migrate`.

В настольном режиме войдите через Telegram и отправьте `/motherlode` без аргументов. Инструмент возвращает камеру из режима от первого лица в обзор; вход в первое лицо недоступен до закрытия предпросмотра. Укажите место мышью, поверните скамейку A/D (15°) и нажмите «Разместить» либо щёлкните по canvas. Esc отменяет предпросмотр до отправки. Дальность 3 м к статике не применяется. Нейтральный ghost показывает только габариты: место проверяет сервер при записи.

После сохранения комната ненадолго приостанавливается и клиенты заново готовят ближайшее окружение без обновления страницы. Новая скамейка получает `placed_<UUID>`, автора в истории `source=game` и сохраняется после перезапуска. Повторная доставка запроса подтверждает тот же экземпляр. У гостей инструмент недоступен; `/vilievna`, каталог моделей и редактирование созданных объектов отложены. Удаление тестового экземпляра пока выполняется офлайн-патчем.

## 1. Из чего состоит карта

| Слой                          | Содержимое                                                                                  | Где редактировать                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Каталог статичных моделей     | Геометрия, цвета, части для прозрачности и коллайдеры целого объекта                        | `content/buildings/ring-block/`                                    |
| Размещение статичных объектов | Ссылка на модель, положение, поворот, включение/отключение каждого экземпляра               | `world_static_instances` в PostgreSQL                              |
| Основание и покрытия          | Земля, газоны, спортивные покрытия, дорожки, парковки, проезды, дороги, островки и разметка | `content/buildings/ring-block/ring-block-ground/source.json`       |
| Фиксированные примитивы       | Четыре граничных препятствия городского мира                                                | `content/worlds/ring-block/world.json`, поле `entities`            |
| Динамические предметы         | Предметы с массой, скоростями, инвентарём и сохранением состояния                           | Каталог `content/items/catalog.json` и отдельная система предметов |
| Метаданные мира               | Границы, точки появления, параметры симуляции, подписи ориентиров                           | `content/worlds/ring-block/world.json`                             |

Дома, светофоры, деревья, кусты, фонари, скамейки, остановки, столбики, памятники, фонтаны, игровые конструкции, стены, киоск и участки ограждений — самостоятельные статичные экземпляры. У светофора опора, корпус и сигналы принадлежат одной модели; у дерева — ствол и крона. Протяжённая ограда может состоять из нескольких самостоятельных участков.

Дороги и разметка сейчас входят в основание. Это цветные плоские многоугольники на небольшой высоте над землёй; при сборке они объединяются с плитой в геометрию с цветами вершин. У покрытий нет собственных строк размещения и отдельных коллайдеров: столкновения обеспечивает плита. Перемещение дома не перемещает прилегающий газон, дорогу или подпись ориентира.

Контрольный состав исходной городской карты на указанную дату: **1744 редактируемых статичных экземпляра, 1675 моделей этих объектов и один рецепт основания**. Сборка превращает основание в 40 плиток по сетке 125 м; вместе с четырьмя границами выпуск содержит 1788 уникальных статичных экземпляров и 1715 моделей. Эти числа описывают исходный контент, а не гарантируют текущее число включённых строк конкретной БД.

Текущие городские модели не используют текстуры-изображения. Деревья формируют параметры instancing без GLB; остальные процедурные рецепты формируют GLB с цветами материалов/вершин. Импорт авторского GLB поддерживается отдельно; изображения в таком файле должны быть встроены в него.

## 2. Источники истины и файлы

| Источник                                             | Назначение                                                                                                |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `content/worlds/ring-block/world.json`               | Заголовок мира, ссылки на каталоги и исходные ячейки, сетка, фиксированные примитивы и метаданные         |
| `content/worlds/ring-block/cells/0_0.json`           | Начальная расстановка — seed для новой БД; массив `buildings` содержит экземпляры любых статичных моделей |
| `content/buildings/ring-block/catalog.json`          | Соответствие `assetId` относительному пути `asset.json`                                                   |
| `content/buildings/ring-block/objects/<assetId>/`    | Рекомендуемое место новых самостоятельных моделей                                                         |
| `content/buildings/ring-block/manual/`, `osm-way-*/` | Существующие авторские модели и дома; исторические имена не запускают импорт                              |
| `world_static_instances`                             | Фактическая расстановка уже инициализированного мира, включая отключённые экземпляры                      |
| `world_layouts`                                      | Принятый выпуск каталога, исходный seed, общая и проверенная ревизии размещения                           |
| `world_static_operations`                            | История SQL-правок, начального наполнения и смены выпуска                                                 |
| `dist/worlds/<worldId>/`                             | Производные ресурсы сборки: модели, коллайдеры, части, ячейки, manifest и `authoring.json`                |

**JSON-расстановка не перезаписывает существующий мир.** Изменение `cells/0_0.json` влияет на первоначальное наполнение новой БД. Чтобы изменить существующий мир, нужны SQL-правки. Чтобы изменение вошло и в будущие новые установки, отдельно внесите его в seed с теми же ID. Удаление всех экземпляров из БД не запускает seed повторно: маркер инициализации сохраняется.

`extraction.json` и эталоны в `tests/fixtures/static-extraction/` — исторические материалы, а не дополнительные источники размещения. Автоматический OSM-конвейер удалён. Сборщик не скачивает геоданные и не восстанавливает объекты по `sourceRef`.

`dist/` не редактируют вручную. Новый статичный объект добавляют в каталог, а его экземпляры — в seed или БД. Динамические предметы добавляют через [систему предметов](items-inventory-and-world-persistence.md); запись в `world_static_instances` не делает объект подвижным.

## 3. Идентификаторы, координаты и размеры

- `assetId` / `asset_id` — ключ модели. Один ключ можно использовать у многих экземпляров. Формат: до 80 символов, строчные латинские буквы, цифры и дефис, первый символ — буква или цифра.
- `entityId` / `entity_id` — постоянный ID экземпляра внутри мира. До 80 символов: латинские буквы, цифры, `_`, `-`. В БД идентичность задаётся парой `(world_id, entity_id)` и не изменяется через `UPDATE`.
- Геометрия и коллайдеры модели задаются в одном локальном пространстве. Рекомендуемый pivot — у основания целого объекта.
- Единицы — метры. Y направлена вверх; земля лежит в плоскости XZ. Для городского мира восток — +X, север — −Z.
- `position` задаёт положение pivot. `rotation` — нормализованный quaternion `{x, y, z, w}`. Для поворота вокруг Y на угол θ: `y = sin(θ/2)`, `w = cos(θ/2)`, `x = z = 0`; θ в радианах. В рецептах `kit` поле `yaw` задаётся в градусах.
- Поля масштаба экземпляра нет. Размеры меняют в модели вместе с её коллайдерами. Изменение модели затрагивает все её экземпляры; для другого размера отдельного объекта создайте другой `assetId`.
- `sourceRef` / `source_ref` — необязательное происхождение `{provider, type, id}`. Оно не управляет загрузкой или импортом.

Сохраняйте `entityId` при перемещении, повороте и смене внешнего вида. Не используйте ID фиксированной земли или границ. Все повёрнутые границы модели и её физические формы должны оставаться внутри границ мира — проверки одного pivot недостаточно.

## 4. Как размещение попадает на клиент

```text
Рецепты каталога + исходный мир
              │ world:build
              ▼
Проверенный выпуск моделей и фиксированное основание
              │ + размещение из PostgreSQL
              ▼
Сервер: общий издатель @su/world-release
              │ вычисление границ и зависимостей ячеек
              ▼
Неизменяемый bundle конкретной версии размещения
              │ HTTP + клиентский CellStreamer
              ▼
Графика и физика нужных ячеек вокруг игрока / камеры
```

Сборщик и сервер используют один алгоритм распределения: полный повёрнутый AABB объекта определяет **все** пересекаемые ячейки. Объект на границе присутствует в нескольких описаниях ячеек с одним `entityId`. Клиент учитывает владельцев и не создаёт его повторно; удаляет экземпляр после освобождения последней нужной ячейки.

Основание разрезается на плитки, самостоятельные объекты сохраняют целостность. Не рассчитывайте ячейки по одному pivot, не дублируйте экземпляр с разными ID ради соседних ячеек и не правьте списки зависимостей в `dist/`.

Для доставки моделей и описаний их частей manifest теперь содержит общие `graphicsPacks`. Клиент проверяет SHA-256 пакета и извлечённых файлов; индивидуальные URL моделей сохраняются для совместимости и повторной загрузки. Коллайдеры загружаются отдельно. Это меняет транспорт ресурсов, сохраняя ID объектов и правила их размещения. Выпуск после применения файлового патча получает пакеты через тот же общий издатель.

Графика и физика загружаются независимо. Используются зоны удержания и задержка освобождения 5 секунд, чтобы объекты не выгружались постоянно на границе области. После освобождения сцены скачанные байты могут оставаться в ограниченном LRU-кеше до 64 МиБ. Выгрузка на клиенте не удаляет строку БД.

Сервер публикует фактическую расстановку в `dist/worlds/<worldId>/layouts/<assetReleaseVersion>/<layoutHash>/`. `authoring.json` связывает сборку с каталогом, seed и фиксированными плитками; его не правят и не раздают клиенту как карту. Подробнее — [потоковая карта](large-map-streaming.md).

## 5. Общий порядок изменения существующего мира

Примеры ниже выполняются из корня репозитория. Нужны Node.js 24+, зависимости и PostgreSQL со схемой v6. Вместо `pnpm` можно использовать `npx --yes pnpm@12.18.0`. Приложение и команды оператора читают `.env` текущего каталога; `DATABASE_URL` выбирает БД, `SU_WORLD` — мир. Создание патча из файлов работает без `.env` и БД.

1. Выберите окружение и мир: `export SU_WORLD=ring-block`. Подготовьте изменения контента и согласованный выпуск приложения.
2. Штатно остановите сервер и дождитесь финального сохранения. Сохраните резервную копию БД и соответствующие исходники/артефакты. Команды экспорта, проверки и миграции тоже требуют свободной блокировки мира.
3. Если меняли каталог, основание или конфигурацию, соберите приложение: `pnpm build`. При необходимости обновления схемы отдельно выполните `pnpm db:migrate:built`.
4. Экспортируйте исходное размещение и подготовьте файловый патч либо SQL-правки.
5. Проверьте и примените изменение. `map-apply` сам подтверждает совместимость геометрии в одной транзакции с размещениями; после прямых SQL-правок нужна `world:migrate`. Затем запустите приложение и обновите вкладку клиента.

### 5.1. Основной сценарий: разработчик без доступа к БД

Оператор один раз готовит актуальные собранные команды через `make build`. Затем при остановленном мире экспортирует размещения:

```sh
make map-export FILE=output/map-base.json
```

По умолчанию выбирается `SU_WORLD` из окружения или `.env`, иначе `ring-block`. Другой мир можно задать так: `SU_WORLD=physics-lab make map-export FILE=output/map-base.json`. Экспорт содержит все редактируемые строки, включая отключённые, версии каталога/seed и ревизии. Фиксированные плитки и границы в него не входят. Если нужно, после экспорта можно снова запустить игру на время подготовки правок; перед проверкой и применением её снова останавливают.

Разработчик получает файл, оставляет исходный экспорт неизменным и редактирует его копию:

```sh
cp output/map-base.json output/map-edited.json
# Изменить instances в map-edited.json.
make map-patch BASE=output/map-base.json EDITED=output/map-edited.json PATCH=output/map.patch.json
```

Разработчику нужны зависимости и собранный `dist/server/layout-command.mjs`; их можно подготовить локально через `make build` без БД. Для запуска из исходников без сборки доступна команда `pnpm world:layout:patch --base output/map-base.json --edited output/map-edited.json --file output/map.patch.json`.

Правила редактирования копии:

- Меняйте только `instances`. Сохраняйте `worldId`, `assetReleaseVersion`, `seedVersion`, `revision` и `instanceRevision` существующих записей.
- Перемещение, поворот, смена модели, `enabled` и `sourceRef` формируют операцию `update` с полной новой записью. Удаление `sourceRef` очищает происхождение.
- Для нового экземпляра задайте уникальный `entityId`, модель из принятого каталога, положение, поворот, `enabled: true` и `instanceRevision: 1`. Не меняйте ID существующего объекта ради перемещения.
- Удалите строку из массива для полного удаления экземпляра; используйте `enabled: false` для обратимого отключения.
- Перестановка строк не считается изменением. Неизвестные поля, повторные ID и некорректные числа/повороты отклоняются при создании патча.

Разработчик передаёт `map.patch.json` вместе с исходным экспортом и описанием изменения, например через PR. Оператор проверяет и применяет его на остановленном мире:

```sh
make map-check PATCH=output/map.patch.json  # полный предварительный прогон, БД не меняется
make map-apply PATCH=output/map.patch.json  # атомарное применение
make map-export FILE=output/map-after.json
make start
```

`FILE` по умолчанию — `output/map-layout.json`, `PATCH` — `output/map-layout.patch.json`. Команды ничего не останавливают и не запускают автоматически. `map-check` и `map-apply` используют те же проверки модели, границ, точек появления и сохранённых предметов, что подготовка мира. Они показывают операции и итоговую ревизию. Дополнительная `world:migrate` после успешного `map-apply` не требуется.

Файловый формат патча v1 содержит `worldId`, `assetReleaseVersion`, `seedVersion`, `baseRevision` и массив `operations`:

| Операция | Поля                                 | Семантика                                                  |
| -------- | ------------------------------------ | ---------------------------------------------------------- |
| `add`    | `op`, `instance`                     | Новый экземпляр, которого ещё нет в БД                     |
| `update` | `op`, `expectedRevision`, `instance` | Полная замена редактируемых полей существующего экземпляра |
| `delete` | `op`, `entityId`, `expectedRevision` | Полное удаление конкретного экземпляра                     |

`instance` содержит `entityId`, `assetId`, `position`, `rotation`, `enabled` и необязательное `sourceRef`; собственная ревизия в операцию не записывается. В одном патче разрешена одна операция на экземпляр. Пропущенные экземпляры остаются без изменений: удаление возможно только явной операцией `delete`.

Патч принимается только при точном совпадении мира, выпуска каталога, seed, общей исходной ревизии и ожидаемых ревизий экземпляров. Любая промежуточная правка размещений делает старый патч неприменимым, даже если затронут другой объект. Получите свежий экспорт и перенесите нужные изменения в его копию; не подгоняйте версии/ревизии вручную. Повторное применение непустого патча отклоняется.

При ошибке применения откатываются все его размещения, ревизии, история и хеш совместимости сохранений. История использует существующий `source: sql`; строки одного применения объединены UUID `operation_id`, который команда выводит в результате. Миграция схемы БД для файловых патчей не нужна. Возможные неактивные файлы неудавшегося выпуска не становятся действующей картой.

Патч меняет только размещения. Он не выпускает новые модели, не меняет землю/границы и не переносит динамические предметы. Сначала оператор принимает новый каталог через сборку и `world:migrate`, затем делает свежий экспорт и размещает новые модели патчем. Эта команда не переписывает seed для будущих установок.

### 5.2. Прямые SQL-правки оператора

SQL-примеры следующих разделов остаются альтернативой файловому патчу. Для изменения только размещений при прежнем выпуске:

```sh
pnpm world:layout:export --file output/map-before.json
# Здесь выполните SQL-транзакцию из нужного сценария ниже.
pnpm world:layout:validate
pnpm world:migrate
pnpm world:layout:export --file output/map-after.json
pnpm start
```

У команд `world:layout:export`, `world:layout:validate` и `world:migrate` есть варианты с суффиксом `:built`, использующие `dist/server/`. Выпуск в `dist/worlds/` должен соответствовать целевым исходникам.

Экспорт — удобная копия размещений, но не резервная копия всей БД. Можно проверить изменённый экспорт без его применения:

```sh
pnpm world:layout:validate --file output/map-candidate.json
```

Проверка полного JSON не меняет размещение в БД. Для применения создайте патч сравнением исходного экспорта с кандидатом и используйте `map-check`/`map-apply`, либо внесите соответствующие SQL-правки. Не редактируйте вручную версии и хеши в `world_layouts`.

SQL выполняйте своим клиентом PostgreSQL в выбранной БД. `psql` сам не читает `.env`; если `DATABASE_URL` уже экспортирована в оболочке, файл правок можно выполнить так:

```sh
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f output/map-change.sql
```

Триггеры блокируют правки при работающем владельце мира, проверяют допустимую модель, числа и quaternion, увеличивают ревизии и записывают историю. Они не заменяют проверку геометрии. `world:layout:validate` проверяет расстановку, точки появления и совместимость сохранённых предметов; `world:migrate` подтверждает выпуск, размещение и совместимость в БД. Пересечение текущего положения или `safePose` предмета с новой статикой может остановить миграцию; автоматического переноса вещей нет. Эти проверки не гарантируют отсутствие всех пересечений между статичными объектами или доступность каждого прохода.

SQL-транзакция правок и последующая `world:migrate` — разные операции. При ошибке проверки уже закоммиченные SQL-правки остаются в БД: исправьте их или восстановите прежние значения отдельной транзакцией, затем повторите проверку. Порядок восстановления всей установки описан в [эксплуатации](operations.md).

## 6. Добавление модели в каталог

### Пример: неподвижный каменный столбик

Создайте `content/buildings/ring-block/objects/stone-bollard-v1/asset.json`:

```json
{
  "formatVersion": 1,
  "assetId": "stone-bollard-v1",
  "source": { "kind": "kit", "file": "source.json" }
}
```

Рядом создайте `source.json`. Это цельный объект высотой 1 м с отдельным простым коллайдером:

```json
{
  "formatVersion": 1,
  "merge": true,
  "parts": [
    {
      "id": "body",
      "role": "detail",
      "fade": false,
      "color": "#707780",
      "shapes": [{ "box": { "center": [0, 0.5, 0], "size": [0.3, 1, 0.3] } }]
    }
  ],
  "colliders": [{ "id": "body", "center": [0, 0.5, 0], "size": [0.3, 1, 0.3] }]
}
```

Добавьте ключ в существующий `assets` городского `catalog.json`, сохранив остальные записи:

```json
"stone-bollard-v1": "objects/stone-bollard-v1/asset.json"
```

Пути к дескрипторам считаются от каталога, пути к рецептам — от дескриптора. Внутри этих путей не допускаются `..`, абсолютные пути и обратные слеши.

Затем:

1. Выполните `pnpm build`. Сборщик выпускает все модели каталога, даже если у новой модели ещё нет экземпляров.
2. Для существующей БД при остановленном мире выполните `pnpm world:layout:validate` и `pnpm world:migrate`. Так БД примет новый выпуск и разрешит новый `asset_id`.
3. Добавьте экземпляр по следующему разделу, затем снова проверьте и примените размещение. До принятия каталога SQL-вставка нового `asset_id` завершится ошибкой `Unknown static asset`.

Для других объектов доступны процедурные `house`, `footprint`, `kit`; `ground` используется основанием. `merge: true` объединяет геометрию внутри целого объекта. Не объединяйте несвязанные деревья, светофоры и ограды в один большой asset.

Для модели из 3D-редактора поддерживается `source.kind: "glb"` с файлами модели и коллайдеров. Нужны GLB 2.0 поддержанного профиля, semantic tags частей (`partId`, `role`, `occlusionGroup`) и совпадающее локальное пространство графики и физики. Внешние ресурсы, анимации и скелеты в профиле статичных моделей не поддерживаются. Полный формат и пример — в [инструкции по моделям](building-assets.md#импорт-модели-из-редактора). Сложность визуальной модели не требует такой же сложности коллайдера; проходы между опорами должны оставаться открытыми в физике.

## 7. Размещение модели на карте

### Существующий мир: запись в БД

Убедитесь, что мир уже инициализирован и модель принята в его каталоге:

```sql
SELECT asset_release_version, revision, validated_revision
FROM world_layouts WHERE world_id = 'ring-block';

SELECT 'stone-bollard-v1' = ANY(asset_ids) AS model_available
FROM world_layouts WHERE world_id = 'ring-block';
```

При остановленном мире добавьте экземпляр. Координаты в примере иллюстративные: выберите свободное место по фактической карте.

```sql
BEGIN;
INSERT INTO world_static_instances (
  world_id, entity_id, asset_id,
  position_x, position_y, position_z,
  rotation_x, rotation_y, rotation_z, rotation_w,
  enabled, source_ref
) VALUES (
  'ring-block', 'courtyard-bollard-001', 'stone-bollard-v1',
  25, 0, 15,
  0, 0, 0, 1,
  true, '{"provider":"manual","type":"bollard","id":"courtyard-bollard-001"}'::jsonb
)
RETURNING entity_id, instance_revision;
COMMIT;
```

Выполните проверку, `world:migrate` и запуск по разделу 5. Для второго экземпляра используйте новый `entity_id` и тот же `asset_id`. Ревизии и `updated_at` вручную не задавайте.

### Начальное наполнение новых миров

Чтобы объект появлялся в новых установках, добавьте запись в `buildings` исходной ячейки `content/worlds/ring-block/cells/0_0.json`:

```json
{
  "entityId": "courtyard-bollard-001",
  "assetId": "stone-bollard-v1",
  "position": { "x": 25, "y": 0, "z": 15 },
  "rotation": { "x": 0, "y": 0, "z": 0, "w": 1 },
  "sourceRef": { "provider": "manual", "type": "bollard", "id": "courtyard-bollard-001" }
}
```

Сохраните остальные записи, включая исходное основание, и пересоберите приложение. Имя исходной ячейки не ограничивает координаты: распределение по пространственным ячейкам выполняется автоматически. В существующей БД такой объект через одну пересборку не появится.

## 8. Перемещение, поворот и замена модели

Посмотрите текущую запись, затем измените только нужные поля. Пример перемещения с поворотом на 90° вокруг Y:

```sql
BEGIN;
UPDATE world_static_instances
SET position_x = 28, position_y = 0, position_z = 18,
    rotation_x = 0, rotation_y = 0.7071067811865475,
    rotation_z = 0, rotation_w = 0.7071067811865476
WHERE world_id = 'ring-block' AND entity_id = 'courtyard-bollard-001'
RETURNING entity_id, asset_id, instance_revision;
COMMIT;
```

Нулевое число изменённых строк означает, что нужный экземпляр не найден. Для замены внешнего вида можно изменить `asset_id` на другую уже принятую модель, сохранив `entity_id`; новые границы и коллайдеры требуют повторной проверки. Для изменения размеров вернитесь к рецепту модели. После правок примените общий порядок из раздела 5.

## 9. Удаление экземпляра из мира

Временное отключение сохраняет запись, но после применения убирает объект из графики и физики:

```sql
BEGIN;
UPDATE world_static_instances SET enabled = false
WHERE world_id = 'ring-block' AND entity_id = 'courtyard-bollard-001'
RETURNING entity_id, enabled, instance_revision;
COMMIT;
```

Для возврата установите `enabled = true` и повторите проверку/миграцию. Отключённая запись по-прежнему должна ссылаться на существующую модель и иметь допустимые координаты и поворот.

Если запись больше не нужна, можно удалить её полностью:

```sql
BEGIN;
DELETE FROM world_static_instances
WHERE world_id = 'ring-block' AND entity_id = 'courtyard-bollard-001'
RETURNING entity_id, asset_id;
COMMIT;
```

История операции сохранится в `world_static_operations`. Примените общий порядок из раздела 5. Удаление экземпляра не удаляет модель из каталога. Если объект также не должен появляться в новых установках, удалите его запись из seed и пересоберите выпуск.

## 10. Удаление модели из каталога

Сначала найдите **все** размещения модели, включая отключённые и размещения в других мирах:

```sql
SELECT world_id, entity_id, enabled
FROM world_static_instances
WHERE asset_id = 'stone-bollard-v1'
ORDER BY world_id, entity_id;
```

Порядок удаления:

1. Проверьте все окружения, которые будут получать новый выпуск. Остановите затронутые миры и сохраните резервные копии.
2. Удалите найденные строки или замените их `asset_id` на сохраняемую модель. Одного `enabled = false` недостаточно.
3. Удалите размещения из всех исходных seed-ячеек, использующих модель. Проверьте ссылки командой `rg -n 'stone-bollard-v1' content docs tests` и разберите назначения совпадений.
4. Удалите запись из соответствующего `catalog.json` и файлы модели, на которые больше никто не ссылается. Учитывайте общие файлы и каталоги других миров.
5. Соберите выпуск, выполните `world:layout:validate` и `world:migrate` для затронутых миров/БД, затем запустите приложение.

Оставшаяся ссылка из seed остановит сборку; ссылка из БД, даже отключённая, остановит проверку нового выпуска. Исторические записи операций, `extraction.json` и независимые эталоны миграции не являются активными размещениями: не удаляйте их автоматически при поиске совпадений. Изменение текущего контента может потребовать осмысленного обновления ожиданий регрессионных тестов; исторический baseline не пересоздают из нового контента ради прохождения проверки.

## 11. Изменение земли, дорог и границ

Основание редактируют в `content/buildings/ring-block/ring-block-ground/source.json`. `min` и `max` задают прямоугольник в XZ, `depth` — толщину плиты, `color` — основной цвет. Каждый элемент `layers` содержит `id`, `color`, `elevation` и `polygons`; полигон задаётся как `[внешний контур, ...контуры отверстий]`, точка — `[x, z]`.

Сейчас используются слои `green`, `park`, `pitch`, `playground`, `footway`, `parking`, `service`, `road`, `islands`, `markings`. Высота покрытия должна быть больше 0 и меньше 0,05 м. Размещайте перекрывающиеся поверхности на разных высотах, чтобы избежать мерцания. Изменение цвета или дорожной геометрии не требует строк `world_static_instances`.

Вспомогательные команды:

```sh
pnpm world:preview-ring  # схема исходного основания и домов → dist/preview/ring.html
pnpm world:ring:layers   # предложение слоёв кольца → dist/preview/ring-layers.json
```

Предпросмотр читает исходные рецепты и seed, а не фактическое размещение БД; он не показывает все типы самостоятельных объектов. Генератор слоёв читает собственные `ring-layout.json` и `ring-trace.json`, но **не переписывает основание автоматически**: результат нужно проверить и осознанно перенести в его рецепт. Это локальные авторские инструменты без OSM-импорта.

После изменения основания, границ мира, граничных препятствий или точек появления пересоберите приложение и выполните общий порядок применения. Фиксированные плитки не отключают и не перемещают через таблицу размещений. Текстовые ориентиры имеют собственные мировые координаты: при перемещении связанного здания скорректируйте `landmarks` отдельно.

## 12. Проверка и завершение изменения

Для изменения контента:

```sh
pnpm build
pnpm test
```

Тесты размещения с PostgreSQL запускаются при заданной `SU_TEST_DATABASE_URL`; без неё соответствующие наборы пропускаются. Используйте отдельную тестовую БД. Для проверки фактических сохранений целевого мира выполняйте офлайн-команды из раздела 5 с его `DATABASE_URL`.

После запуска проверьте изменённое место в игре: видимость, коллизии, проходы, появление персонажа, уход из области загрузки и возвращение. Для объекта на границе ячеек проверьте обе стороны; для общей модели — несколько её экземпляров. Сравните экспорт размещений до/после и убедитесь, что изменились только нужные строки.

В ревью передавайте изменения каталога/рецептов/seed, файловый патч размещений либо явную SQL-инструкцию для существующих БД. Коммит JSON не переносит рабочую расстановку из БД в другую установку. В документе поставки укажите мир, исходный и целевой выпуски, порядок применения и восстановления.

Основные точки реализации для проверки актуальности памятки: [сборщик](../tools/world-build/src/index.ts), [форматы и проверки](../packages/contracts/src/world-bundle.ts), [общий издатель](../packages/world-release/src/index.ts), [схема размещений](../apps/server/src/layout/schema.ts), [хранилище](../apps/server/src/layout/store.ts), [подготовка мира](../apps/server/src/layout/prepare.ts), [команды экспорта и проверки](../apps/server/src/layout-command.ts), [миграция](../apps/server/src/migrate-world.ts), [клиентский загрузчик](../apps/client/src/streaming/cells.ts).
