# Эксплуатация

Текущая версия работает в production; все приёмки завершены по подтверждению владельца проекта от 12 ноября 2026 года. Ниже — команды запуска и обслуживания этой реализации.

## Собранная версия

Если установлен `make`, пересобрать приложение и запустить сервер можно одной командой:

```sh
make run
```

Просто `make` выполняет то же самое. Перед первым запуском установите зависимости командой `make install`. Нужен Node.js 24 или новее; Makefile использует pnpm 12.18.0 через `npx`, поэтому глобальная установка pnpm не обязательна. При ошибке сборки или миграций сервер не запускается.

Отдельно доступны `make build` (сборка) и `make start` (запуск уже собранной версии). Переменные окружения передаются серверу, например: `HOST=127.0.0.1 PORT=2567 make run`. Остановка — `Ctrl+C`.

`make run` последовательно собирает приложение, применяет SQL-миграции и проверяет сохранённый мир на новой карте перед запуском сервера. Совместимые обновления карты применяются автоматически с сохранением предметов и инвентарей. Для новой базы первоначальное наполнение создаётся при запуске сервера. Если обновлённая карта несовместима с сохранёнными предметами, запуск останавливается без изменения сохранённого мира. `make start` и `pnpm start` запускают уже собранный сервер и только проверяют версии; миграции для них выполняются отдельно.

## Обновление существующей установки

Штатно остановите сервер, дождитесь финального сохранения и сделайте согласованную резервную копию PostgreSQL. Сохраните соответствующую версию кода/артефактов. Затем выполните из корня проекта для того же `SU_WORLD`:

```sh
make build
npx --yes pnpm@12.18.0 db:migrate:built
npx --yes pnpm@12.18.0 world:migrate:built
make start
```

`world:migrate:built` читает `.env` и собранную карту `dist/worlds/ring-block`; другой мир выбирается через `SU_WORLD`. Она блокирует одновременный запуск этого мира, проверяет типы предметов и все сохранённые положения в новой физической сцене. Только после успешной проверки обновляется хеш совместимости. Предметы, инвентари и история операций сохраняются без изменений; первоначальное наполнение повторно не создаётся. Если текущая поза пересекает статическое препятствие или выходит за границы, либо сохранённая `safePose` несовместима со статической геометрией и границами, миграция откатывается. Допустимый снимок движущегося предмета в воздухе сохраняется вместе со скоростями; автоматически переносить его на `safePose` не требуется. Изменение физических параметров существующих типов эта команда также отклоняет. В собранной поставке доступен `node dist/server/migrate-world.mjs`. SQL-команда `db:migrate` обновляет структуру таблиц отдельно от геометрии мира.

Те же действия без `make`, после установки зависимостей:

```sh
npx --yes pnpm@12.18.0 build
npx --yes pnpm@12.18.0 db:migrate:built
npx --yes pnpm@12.18.0 world:migrate:built
npx --yes pnpm@12.18.0 start
```

Откройте **http://127.0.0.1:2567**. Один Node.js-процесс обслуживает клиент, данные мира и WebSocket. Сборка находится в `dist/`, включая локальную копию Havok WASM. Запускать `start` нужно из корня репозитория; после изменений исходников повторите `build`. PostgreSQL с применёнными миграциями обязателен, включая гостевую игру. Docker, CI и публикация для локальной работы не нужны.

## Production: meta.ftagn.xyz

На сервере `ftagn.xyz` Caddy направляет **https://meta.ftagn.xyz** на **127.0.0.1:2567**. Используется собранная версия: один процесс обслуживает страницу, API и WebSocket игры. Порт **5173** относится только к Vite в режиме `dev`; домен настроен на порт **2567**.

Для обновления сначала выполните остановку и резервное копирование из раздела выше. В консоли сервера подготовьте сборку из корня проекта:

```sh
cd /root/local-repo/syktyvkar-underground
npx --yes pnpm@12.18.0 install --frozen-lockfile
npx --yes pnpm@12.18.0 build
npx --yes pnpm@12.18.0 db:migrate:built
npx --yes pnpm@12.18.0 world:migrate:built
```

Затем запускайте приложение одной командой из этого же каталога:

```sh
HOST=127.0.0.1 PORT=2567 node dist/server/main.mjs
```

Для пересборки и запуска одной командой из текущего рабочего каталога используйте `make run`.

Откройте **https://meta.ftagn.xyz** и нажмите «Войти». Процесс работает в текущей консоли, журналы выводятся туда же; `Ctrl+C` останавливает игру. Для работы после отключения SSH можно запускать эту команду внутри `tmux`. Пока процесс остановлен, домен возвращает **502 Bad Gateway**. При новом запуске предметы и инвентари восстанавливаются из PostgreSQL. CI, Docker, deploy и отдельный сервис приложения для этого режима не требуются.

Проверка при запущенном приложении:

```sh
curl -fsS https://meta.ftagn.xyz/health/ready
# {"ready":true}
```

Настройка домена находится на сервере в `/etc/caddy/sites/meta.ftagn.xyz.caddy`; её подключает существующий `/etc/caddy/Caddyfile`:

```caddyfile
meta.ftagn.xyz {
    encode zstd gzip
    reverse_proxy 127.0.0.1:2567
}
```

Caddy обслуживает HTTPS и перенаправляет HTTP на HTTPS. [Обычный `reverse_proxy` поддерживает WebSocket](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#streaming), поэтому отдельные маршруты для игрового соединения не нужны. Перезапуск игры и пересборка не требуют перезагрузки Caddy.

## Постоянные аккаунты через Telegram

Сервер автоматически читает `.env` из текущего рабочего каталога. Для мира всегда нужен `DATABASE_URL`. Чтобы включить аккаунты, дополнительно задайте все три параметра: `PUBLIC_ORIGIN`, `CLIENT_ID`, `CLIENT_SECRET`:

```dotenv
PUBLIC_ORIGIN=https://meta.ftagn.xyz
CLIENT_ID=идентификатор_из_BotFather
CLIENT_SECRET=секрет_из_BotFather
DATABASE_URL=postgresql://su_app:пароль@127.0.0.1:5432/syktyvkar_underground
```

В BotFather включите OpenID Connect Login, зарегистрируйте Redirect URI `https://meta.ftagn.xyz/api/auth/telegram/callback` и оставьте алгоритм `RS256`. Запрашивается только `openid`. Обмен кодом и проверка подписи выполняются сервером; Trusted Origins и Native Login для этого сценария не требуются. Игровые имя, цвет и внешность задаются отдельно от Telegram.

Обмен кодом использует `client_secret_post`: `client_id` и `client_secret` передаются как поля формы по HTTPS. Этот метод используется текущей интеграцией Telegram. В текущей интеграции вариант с HTTP Basic возвращал `invalid_client`. При отказе входа сервер пишет `Telegram login failed` с безопасными кодами протокола и именем проверяемого поля; содержимое токенов, секреты и текст ответа провайдера в журнал не попадают.

Перед первым запуском с аккаунтами примените миграции отдельной командой:

```sh
npx --yes pnpm@12.18.0 db:migrate
npx --yes pnpm@12.18.0 build
HOST=127.0.0.1 PORT=2567 node dist/server/main.mjs
```

В собранной поставке миграции доступны через `node dist/server/migrate.mjs`. Запуск из корня проекта подхватывает `.env`. Миграции можно выполнять повторно; обычный запуск сервера только проверяет версию схемы. При откате кода созданные таблицы сохраняйте. Если `PUBLIC_ORIGIN`, `CLIENT_ID`, `CLIENT_SECRET` отсутствуют, доступен гостевой режим с обязательным `DATABASE_URL`. Частичный набор этих трёх параметров считается ошибкой. Без PostgreSQL сервер не запускается.

На стартовом экране доступна кнопка «Войти через Telegram». Первый подтверждённый вход создаёт аккаунт, повторный находит его по проверенным `iss` и `sub`. Имя, цвет и скин сохраняются кнопкой «Сохранить профиль» или перед входом в мир, если настройки изменены. Настройки переживают перезапуск игры и доступны в другом браузере после входа через тот же Telegram. Устаревшая форма из другой вкладки получает конфликт и актуальный профиль. Для обновления существующей БД до схемы v3 со скинами выполните `pnpm db:migrate` перед запуском новой версии.

В одном аккаунте одновременно доступен один персонаж, включая подготовку и 30-секундное окно восстановления связи. Для второго независимого игрока используйте другой Telegram или гостевой режим. Кнопка «Выйти» покидает мир; «Выйти из аккаунта» также отзывает авторизацию текущего браузера, закрывает его игровые соединения и отменяет резерв восстановления. Другие браузеры сохраняют свои авторизации. Сессия действует до 30 дней; в БД хранится хеш случайного токена, в браузере — HttpOnly cookie. Внешний провайдер нужен при новом входе, а игровые сообщения обрабатываются нашим сервером.

При недоступности PostgreSQL операции аккаунта возвращают `503`; изменение профиля считается сохранённым только после успешной записи. Запросы к БД выполняются вне физического шага. `/health/ready` проверяет готовность мира и подключение к БД. PostgreSQL обязателен и для гостевого мира. При ошибке записи физика приостанавливается, готовность снимается; после восстановления связи сервер устанавливает результаты незавершённых операций, согласует тела и возобновляет игру. Позиция персонажа между запусками не сохраняется. Для реальных аккаунтов настройте резервное копирование базы и проверку восстановления.

Для локальной проверки OIDC потребуется отдельно зарегистрированный callback и соответствующий `PUBLIC_ORIGIN`, например `http://127.0.0.1:5173` при работе через Vite. Production-настройка `https://meta.ftagn.xyz` предназначена для запуска через этот домен.

## Конфигурация

Сервер и команды миграции читают `.env` из текущего рабочего каталога. Не публикуйте файл с секретами. Шаблон — [`.env.example`](../.env.example).

| Параметр | Назначение / значение по умолчанию |
| --- | --- |
| `DATABASE_URL` | Обязательное подключение к PostgreSQL |
| `PUBLIC_ORIGIN`, `CLIENT_ID`, `CLIENT_SECRET` | Полный набор для Telegram OIDC; без него остаётся гостевой вход |
| `HOST` | Адрес сервера, по умолчанию `127.0.0.1` |
| `PORT` | Порт HTTP/WS, по умолчанию `2567` |
| `SU_WORLD` | `ring-block` по умолчанию; также `physics-lab`, `streaming-lab` |
| `SU_ITEM_CREATION_ENABLED` | `true` по умолчанию; `false` отключает только новые выдачи `/giveme` |

Vite в режиме `pnpm dev` обслуживает порт 5173 и проксирует API/WS к 2567. Производственная сборка обслуживается одним сервером на 2567. `SU_WORLD` должен совпадать при миграции и запуске.

## Восстановление и диагностика

`GET /health/live` сообщает о работе процесса. `GET /health/ready` возвращает 200 только при готовом мире и доступной БД; иначе 503. `/api/world` содержит активную комнату, версии и наличие места; `/api/diagnostics` — метрики мира.

При сбое БД физика приостанавливается. Сервер сохраняет очередь, устанавливает исход незавершённых операций, согласует физические тела с БД и возобновляет игру. Не заменяйте существующее сохранение начальным наполнением. Штатная остановка ждёт финальную запись до 10 секунд; ошибка сопровождается ненулевым кодом выхода и сообщением о неполном сохранении.

После обновления несовместимого протокола старые вкладки должны перезагрузиться. При отказе миграции сохранённые данные не меняются: исправьте несовместимость геометрии/типов и повторите проверку. Автоматического переноса предметов в новые места нет.

Возврат к старому коду требует совместимой БД и артефактов. Восстановление старого backup после новых игровых операций потеряет эти операции; переключение кода само по себе не является откатом данных. SQL-таблицы и записи применённых миграций вручную не удаляются.

Проверки аккаунтов, предметов, миграций и перезапуска — в [testing.md](testing.md). Устройство постоянного мира — в [документе предметов](items-inventory-and-world-persistence.md).
