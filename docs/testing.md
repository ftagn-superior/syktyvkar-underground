# Проверки изменений

Текущая production-версия принята: все приёмки завершены по подтверждению владельца проекта от 12 ноября 2026 года. Этот документ описывает воспроизведение проверок для следующих изменений. Исторические результаты и ограничения конкретных стендов — в [reports](../reports/README.md).

## Подготовка

Нужны зависимости из lockfile, Node.js ≥24 и pnpm 12.18.0; зафиксированная версия Node — в `.node-version`.

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm check
pnpm test
pnpm build
```

`pnpm check` проверяет TypeScript и границы пакетов. `pnpm test` запускает Vitest: контракты, сборщик, физику, клиентскую логику и интеграционные сценарии. **Без `SU_TEST_DATABASE_URL` PostgreSQL-зависимые тесты пропускаются**; такой запуск не проверяет сохранность данных. Для полного набора передайте эту переменную через окружение тестового процесса. Не выводите строку подключения в отчёты.

`test:accounts`, `test:items` и браузерные команды через `tools/test-database.mjs` читают `.env`, берут `SU_TEST_DATABASE_URL` либо `DATABASE_URL` и передают её тестам. Обычный `pnpm test` не использует этот wrapper. Фикстуры создают случайные временные схемы и удаляют их после завершения; роль тестовой БД должна уметь создавать схемы. Для проверок используйте тестовое подключение.

Браузерные сценарии запускаются после сборки. Большинство поднимает отдельный сервер; сценарии, ожидающие внешний сервер, перечислены отдельно ниже. Тестовые миры по умолчанию используют `physics-lab`, если сценарий не выбирает другой контент.

## Подсистемы

| Проверка | Команда |
| --- | --- |
| Аккаунты, профиль, локальный OIDC с RS256 | `pnpm test:accounts`, `pnpm test:accounts:browser` |
| Хранение, сетевые операции, миграции и физика предметов | `pnpm test:items`, `pnpm test:items:browser` |
| Выдача предметов и приватность ответов | `pnpm test:giveme:browser` |
| Эквивалентность физики Node/Chromium | `pnpm test:physics:browser` |
| GLB, независимая прозрачность, свободный поворот клавишами и мышью, движение с произвольных ракурсов и коллизии | `pnpm test:buildings:browser` |
| Повреждённый кеш и неверные ресурсы | `pnpm test:assets:browser` |
| Скины, походка, возврат и переподключение | `pnpm test:avatars:browser` |
| Реакции, выбираемые анимации, чат | `pnpm test:reactions:browser`, `pnpm test:animations:browser`, `pnpm test:chat:browser` |
| Перезапуск и восстановление | `pnpm test:restart:browser` |
| Город, подготовка, камера 30× и выход в просмотр | `pnpm test:dynamic-map:browser` |

Настоящий вход через Telegram проверяется на зарегистрированном callback; локальный OIDC-провайдер проверяет протокол и поведение приложения, не доступность внешнего провайдера.

## Внешний тестовый сервер

Этим сценариям нужен уже запущенный сервер с тестовыми сохранениями; адрес задаётся `SU_TEST_URL` (по умолчанию `http://127.0.0.1:2567`):

```sh
pnpm test:browser
pnpm test:polish:browser
pnpm test:render:browser
pnpm test:soak
```

`test:browser` проверяет два контекста, заполнение комнаты и восстановление; `test:soak` — 30 минут с шестью SDK-клиентами и двумя браузерами. Для них нужен мир без других участников; длительность soak задаёт `SU_SOAK_SECONDS`. `test:polish:browser` проверяет фокус, графический контекст, качество и диагностический отчёт. Для сравнения графики оставьте одного игрока.

Нагрузка на отдельный тестовый сервер:

```sh
pnpm load -- --clients 6 --seconds 60 --scenario crowd --report output/validation/load.json
```

`spread` проверяет распределённое движение, `crowd` — скопление. Два дополнительных браузера дают восемь участников. `--seconds 1800` задаёт длительный прогон, `--url` — адрес. Генератор использует обычный SDK и команды движения.

## Потоковая карта и сеть

`SU_TEST_DATABASE_URL` обязателен для изолированных постоянных миров. Команды L0–L4 сохранены как имена регрессионных сценариев, а не как незавершённые этапы проекта.

| Команда | Область |
| --- | --- |
| `pnpm test:large-map:l0`, `pnpm test:large-map:l1` | Базовые механизмы, сетка и выпуск пакета |
| `pnpm test:large-map:l2` | Подключение/освобождение графики и физики |
| `pnpm test:large-map:l3` | Вход, движение через ячейки, возврат, переподключение |
| `pnpm test:large-map:l4` | AOI, локальные наборы сущностей и ресурсы |
| `pnpm test:streaming:browser` | Комбинированные браузерные проверки потоковой карты |
| `pnpm test:streaming:load` | Один профиль нагрузки |
| `pnpm test:streaming:matrix` | Матрица 2/4/8 участников и сценариев |
| `pnpm test:streaming:soak` | По 30 минут spread и crowd по умолчанию |
| `pnpm test:streaming:verify` | Составной прогон проверок; включает Linux netem по умолчанию |
| `pnpm test:streaming:evidence` | Сводка сохранённых свидетельств |

Профили `test:streaming:load`:

- `SU_STREAMING_CONTENT=ring-block|streaming-lab`, `SU_STREAMING_ITEMS=existing|all-types`.
- `SU_STREAMING_SCENARIO=spread|crowd`, `SU_STREAMING_CLIENTS=2|4|8`, `SU_STREAMING_ZOOM=1|30`.
- `SU_STREAMING_SECONDS`, `SU_STREAMING_WARMUP` — длительность и прогрев в секундах.
- `SU_STREAMING_RENDERER=software|hardware`, `SU_STREAMING_QUALITY=economy|standard`, `SU_STREAMING_WIDTH`, `SU_STREAMING_HEIGHT`, `SU_STREAMING_OUTPUT`.

Профиль `all-types` включает все пять типов и начальные движущиеся снимки. Для целевого GPU задавайте `hardware`, обычное качество и 1920 × 1080 явно: значения по умолчанию предназначены для программного функционального стенда.

После сборки `node --import tsx tests/streaming-regression.ts` запускает набор функциональных регрессий. `pnpm test:network` проверяет задержки и джиттер со своими серверами; для видеозаписей нужен `pnpm exec playwright install chromium ffmpeg`.

`pnpm test:network:netem` и `pnpm test:streaming:netem` проверяют потери TCP в отдельном Linux network namespace. Нужны `unshare`, `ip`, `tc`, `curl`, соответствующие права и доступный тестовый PostgreSQL; streaming-netem использует Unix socket. Удаление сообщений приложения не эквивалентно потере TCP-пакетов.

## Измерения и свидетельства

`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` выбирает установленный Chromium. Функциональные сценарии обычно используют SwiftShader. `SU_TEST_RENDERER=hardware` отключает принудительный программный рендерер в общих браузерных helpers; фактический рендерер фиксируется в отчёте.

`test:render:browser` сравнивает качество при 1280 × 720: по умолчанию 10 секунд прогрева и 15 секунд измерений. Настройки — `SU_PROFILE_WARMUP_MS`, `SU_PROFILE_SAMPLE_MS`, `SU_PROFILE_QUALITIES`, `SU_PROFILE_OUTPUT`. `test:avatars:profile` измеряет изолированную сцену с восемью персонажами и клипами, без города и сетевой нагрузки. Эти короткие профили не заменяют полный нагрузочный сценарий.

Для сопоставления регрессий сохранены бюджеты интегрированной версии:

| Метрика | Референсный критерий |
| --- | --- |
| Полный серверный цикл, включая AOI/кодирование | p95 ≤8 мс, p99 <16,7 мс; сервер 2 vCPU / 4 ГБ |
| Видимый кадр, включая подключение ячеек | p95 ≤20 мс, целевой GPU, 1920 × 1080, обычное качество, 60 секунд прогрева |
| Коррекции до сглаживания | p95 ≤0,2 м у статики, ≤0,5 м при контакте с предметом; RTT 100 мс, jitter ±20 мс |
| Сходимость остановленного контрольного ящика | До 0,1 м за 500 мс после свежего состояния |
| WebSocket-состояние | Среднее ≤30 КиБ/с на клиента за устойчивые 60 секунд при восьми участниках |
| Обязательные ресурсы до первой игры | ≤8 МиБ сжатых ресурсов; дальний фон измеряется отдельно |
| Стабильность | По 30 минут spread и crowd, ограниченные очереди/кеши, отсутствие накопления ресурсов |

Фиксируйте версию кода/мира, оборудование и рендерер, качество/окно/масштаб, количество и типы предметов, число клиентов, прогрев и размер выборки. HTTP и WS учитываются отдельно. Телепортации не смешиваются с обычными коррекциями; пики не скрываются за квантилями. Сценарий 30× измеряется отдельно. Для серверного профиля браузеры и генераторы запускаются вне измеряемых 2 vCPU / 4 ГБ.

Машинные журналы, снимки и видео находятся в `output/`, исключённом из Git. Краткие отчёты сохраняются в `reports/`. Старый отчёт подтверждает свой прогон, а не автоматически каждый последующий коммит. Восемь участников не подтверждают поддержку 50.
