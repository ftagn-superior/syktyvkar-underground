# Проверки изменений

Карточки всех моделей проверяются командой `pnpm world:catalog:check --sources`
(также входит в `pnpm check`). После `pnpm world:build` выполните
`pnpm world:catalog:check`: проверяются опубликованный индекс, SHA-256, ссылки на
ресурсы выпуска и актуальность метаданных. Сборка создаёт каталог автоматически.
Формат и регрессии — в [инструкции каталога моделей](world-model-catalog.md).

Текущая production-версия принята: все приёмки завершены по подтверждению владельца проекта от 12 ноября 2026 года. Этот документ описывает воспроизведение проверок для следующих изменений. Ручная мобильная приёмка нового сенсорного MVP остаётся открытой; автоматические результаты — в [отчёте](../reports/touch-controls-mvp.md). Исторические результаты и ограничения конкретных стендов — в [reports](../reports/README.md).

Каталог и размещение статики проверяются на отдельной **тестовой** PostgreSQL:

```sh
export SU_TEST_DATABASE_URL=postgresql://.../test_database
pnpm check
pnpm test
pnpm build
pnpm test:static-placement:browser
pnpm test:static-removal:browser
pnpm test:static-removal:city
SU_STATIC_PLACEMENT_WORLD=ring-block pnpm test:static-placement:browser
pnpm test:chat:browser
pnpm test:giveme:browser
pnpm test:items:browser
```

Для медленного стенда с городскими fixtures допустим `pnpm test --testTimeout=120000 --hookTimeout=120000`. Это лимит тестового runner; клиентский барьер по-прежнему ограничен 15 секундами.

Новый сценарий сам создаёт маленький выпуск с реальной скамейкой, локальный OIDC, два браузерных контекста и временную схему. SDK-проверки находятся в `tests/integration/static-placement.test.ts`, `placement-catalog.test.ts` и `placement-catalog-city.test.ts`, геометрия — в `packages/simulation/src/static-placement.test.ts`. Без `SU_TEST_DATABASE_URL` SQL-наборы пропускаются и не подтверждают готовность MVP. Свидетельства браузера записываются в `output/playwright/static-placement*`; текущие результаты и измерения — в [отчёте каталога](../reports/motherlode-placement-catalog.md). Исторические замеры ядра сохранены в [прежнем отчёте](../reports/static-placement-core-mvp.md).

Удаление проверяют `tests/integration/static-removal.test.ts`, `packages/simulation/src/static-removal.test.ts`, клиентские контракты/состояния и `rendering/static-selection.test.ts`. Браузерный сценарий `test:static-removal:browser` использует два клиента, исходное здание вне палитры, два одинаковых экземпляра скамейки и процедурное дерево; проверяет отмену, выход из первого лица, блокировку движения, потерю фокуса/ответа и перезапуск. `test:static-removal:city` проверяет выбор и удаление исходного здания в настоящем `ring-block`, общую паузу и двух клиентов. Все записи используют временную изолированную схему PostgreSQL. Свидетельства: `output/playwright/static-removal/` и `output/playwright/static-removal-city/`.

## Сохранение позиции игрока

После сборки задайте выделенный **тестовый** `SU_TEST_DATABASE_URL`. Эти проверки используют временные схемы и не подставляют `DATABASE_URL` вместо него:

```sh
pnpm check
pnpm build
pnpm exec vitest run packages/simulation/src/player-spawn.test.ts apps/server/src/players/position-runtime.test.ts tests/integration/player-position-store.test.ts tests/integration/player-positions.test.ts tests/integration/player-position-failures.test.ts apps/client/src/network/session.test.ts
pnpm test:player-positions:browser
```

SQL-наборы проверяют обновление схемы 6 → 7, упорядочивание снимков, блокировку смены эпохи, тайм-ауты и освобождение соединений. WebSocket-набор проверяет вход, выход, reconnect, отказ подготовки, финальную физическую проверку и рестарт. Браузерный сценарий использует локальный OIDC и игровой ввод. Свидетельства: `output/playwright/player-positions/`; результаты и воспроизводимый городской стенд — в [отчёте](../reports/player-position-persistence-mvp.md). Ручные шаги полного города перечислены в [плане](plans/player-position-persistence-mvp.md#15-ручная-игровая-приёмка-и-критерий-готовности) и выполняются отдельно.

## Подготовка

Нужны зависимости из lockfile, Node.js ≥24 и pnpm 12.18.0; зафиксированная версия Node — в `.node-version`.

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm check
pnpm test
pnpm build
```

`pnpm check` проверяет TypeScript и границы пакетов. `pnpm test` запускает Vitest: контракты, сборщик, физику, клиентскую логику и интеграционные сценарии. **Без `SU_TEST_DATABASE_URL` PostgreSQL-зависимые тесты пропускаются**; такой запуск не проверяет сохранность данных. Для полного набора передайте эту переменную через окружение тестового процесса. Не выводите строку подключения в отчёты.

`test:accounts`, `test:items` и браузерные команды через `tools/test-database.mjs` читают `.env`, берут `SU_TEST_DATABASE_URL` либо `DATABASE_URL` и передают её тестам. Обычный `pnpm test` не использует этот wrapper. Фикстуры создают случайные временные схемы и удаляют их после завершения; роль тестовой БД должна уметь создавать схемы. Для проверок используйте тестовое подключение.

Браузерные сценарии запускаются после сборки. Большинство поднимает отдельный сервер; сценарии, ожидающие внешний сервер, перечислены отдельно ниже. Тестовые миры по умолчанию используют `physics-lab`, если сценарий не выбирает другой контент.

## Сенсорное управление

После `pnpm build` задайте **тестовый** `SU_TEST_DATABASE_URL` и выполните `pnpm test:touch:browser`. Сценарий сам создаёт отдельный мир с близким предметом, временную схему PostgreSQL и локальный OIDC, проверяет авторизованного игрока. Chromium получает настоящие касания через CDP, включая несколько одновременных пальцев; вызовы игровых обработчиков не используются.

Проверяются аналоговая скорость и мировые направления, независимый захват и отпускание пальцев, отмена, изменение экрана, фокус/фон, WebGL, служебные кнопки, ограничения социальных панелей и инвентаря, смена способа ввода и отмена размещения, масштабы рендера при DPR 1/2/3. Свидетельства сохраняются в `output/playwright/touch/`.

Chromium под автоматизацией оставляет фоновые страницы видимыми даже в оконном режиме на текущем стенде. Сценарий проверяет настоящий blur при смене вкладок и отдельно моделирует visibilitychange, явно отмечая это в JSON-отчёте. Настоящее скрытие страницы проверяется при ручной мобильной приёмке.

Перед мобильной приёмкой на **iPhone/Safari, Android/Chrome и хотя бы одном планшете** пройдите в полном городе обе ориентации: вход → несколько минут ходьбы со свайпом → остановка → сворачивание/возврат → «На старт» → выход. На гибридном устройстве проверьте мышь/клавиатуру. Запишите модель, ОС, браузер, качество и проблемы. Эмуляция SwiftShader не подтверждает мобильный FPS. Для графики на 390 × 844 CSS-пикселях ожидаются 390 × 844 в standard и 260 × 562 в economy при любом DPR.

## Внешний тестовый сервер

Этим сценариям нужен уже запущенный сервер с тестовыми сохранениями; адрес задаётся `SU_TEST_URL` (по умолчанию `http://127.0.0.1:2567`):

```sh
pnpm test:browser
pnpm test:polish:browser
pnpm test:render:browser
pnpm test:soak
```

`test:browser` проверяет два контекста, заполнение комнаты и восстановление; `test:soak` — 30 минут с шестью SDK-клиентами и двумя браузерами. Для них нужен мир без других участников; длительность soak задаёт `SU_SOAK_SECONDS`. `test:polish:browser` проверяет фокус, графический контекст, качество и диагностический отчёт. Для сравнения графики оставьте одного игрока.

Нагрузка на отдельный тестовый сервер:

```sh
pnpm load -- --clients 6 --seconds 60 --scenario crowd --report output/validation/load.json
```

`spread` проверяет распределённое движение, `crowd` — скопление. Два дополнительных браузера дают восемь участников. `--seconds 1800` задаёт длительный прогон, `--url` — адрес. Генератор использует обычный SDK и команды движения.

## Потоковая карта и сеть

`SU_TEST_DATABASE_URL` обязателен для изолированных постоянных миров. Команды L0–L4 сохранены как имена регрессионных сценариев, а не как незавершённые этапы проекта.

| Команда                                            | Область                                                      |
| -------------------------------------------------- | ------------------------------------------------------------ |
| `pnpm test:large-map:l0`, `pnpm test:large-map:l1` | Базовые механизмы, сетка и выпуск пакета                     |
| `pnpm test:large-map:l2`                           | Подключение/освобождение графики и физики                    |
| `pnpm test:large-map:l3`                           | Вход, движение через ячейки, возврат, переподключение        |
| `pnpm test:large-map:l4`                           | AOI, локальные наборы сущностей и ресурсы                    |
| `pnpm test:streaming:browser`                      | Комбинированные браузерные проверки потоковой карты          |
| `pnpm test:streaming:load`                         | Один профиль нагрузки                                        |
| `pnpm test:streaming:matrix`                       | Матрица 2/4/8 участников и сценариев                         |
| `pnpm test:streaming:soak`                         | По 30 минут spread и crowd по умолчанию                      |
| `pnpm test:streaming:verify`                       | Составной прогон проверок; включает Linux netem по умолчанию |
| `pnpm test:streaming:evidence`                     | Сводка сохранённых свидетельств                              |

Профили `test:streaming:load`:

- `SU_STREAMING_CONTENT=ring-block|streaming-lab`, `SU_STREAMING_ITEMS=existing|all-types`.
- `SU_STREAMING_SCENARIO=spread|crowd`, `SU_STREAMING_CLIENTS=2|4|8`, `SU_STREAMING_ZOOM=1|30`.
- `SU_STREAMING_SECONDS`, `SU_STREAMING_WARMUP` — длительность и прогрев в секундах.
- `SU_STREAMING_RENDERER=software|hardware`, `SU_STREAMING_QUALITY=economy|standard`, `SU_STREAMING_WIDTH`, `SU_STREAMING_HEIGHT`, `SU_STREAMING_OUTPUT`.

Профиль `all-types` включает все пять типов и начальные движущиеся снимки. Для целевого GPU задавайте `hardware`, обычное качество и 1920 × 1080 явно: значения по умолчанию предназначены для программного функционального стенда.

После сборки `node --import tsx tests/streaming-regression.ts` запускает набор функциональных регрессий. `pnpm test:network` проверяет задержки и джиттер со своими серверами; для видеозаписей нужен `pnpm exec playwright install chromium ffmpeg`.

`pnpm test:network:netem` и `pnpm test:streaming:netem` проверяют потери TCP в отдельном Linux network namespace. Нужны `unshare`, `ip`, `tc`, `curl`, соответствующие права и доступный тестовый PostgreSQL; streaming-netem использует Unix socket. Удаление сообщений приложения не эквивалентно потере TCP-пакетов.

## Измерения и свидетельства

После `pnpm world:build` команда `pnpm test:loading:browser` собирает текущий production-клиент отдельно в `output/playwright/loading-profile/` и запускает локальный сервер только для чтения. БД и игровая комната не требуются. По умолчанию выполняются три холодных загрузки, одна тёплая и холодная с добавленными 20 мс на ответ; это синтетическая задержка, не измерение сетевого RTT. Результат содержит время готовности видимой области и всего заказанного окружения, запросы и байты, объекты сцены, кадры загрузки и длинные задачи. Проверяются отсутствие WASM-запросов и физических тел до входа.

Параметры: `SU_PROFILE_COLD_RUNS=1..5`, `SU_PROFILE_QUALITY=economy|standard`, `SU_PROFILE_OUTPUT` (каталог), `SU_PROFILE_WORLD_DIRECTORY`, `SU_PROFILE_ZOOM=1` (дополнительно 30× и возврат), `SU_TEST_RENDERER=hardware` для обычного графического backend. Программный профиль не подтверждает производительность Safari или аппаратный FPS.

`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` выбирает установленный Chromium. Функциональные сценарии обычно используют SwiftShader. `SU_TEST_RENDERER=hardware` отключает принудительный программный рендерер в общих браузерных helpers; фактический рендерер фиксируется в отчёте.

`test:render:browser` сравнивает качество при 1280 × 720: по умолчанию 10 секунд прогрева и 15 секунд измерений. Настройки — `SU_PROFILE_WARMUP_MS`, `SU_PROFILE_SAMPLE_MS`, `SU_PROFILE_QUALITIES`, `SU_PROFILE_OUTPUT`. `test:avatars:profile` измеряет изолированную сцену с восемью персонажами и клипами, без города и сетевой нагрузки. Эти короткие профили не заменяют полный нагрузочный сценарий.

Для сопоставления регрессий сохранены бюджеты интегрированной версии:

| Метрика                                        | Референсный критерий                                                                  |
| ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| Полный серверный цикл, включая AOI/кодирование | p95 ≤8 мс, p99 <16,7 мс; сервер 2 vCPU / 4 ГБ                                         |
| Видимый кадр, включая подключение ячеек        | p95 ≤20 мс, целевой GPU, 1920 × 1080, обычное качество, 60 секунд прогрева            |
| Коррекции до сглаживания                       | p95 ≤0,2 м у статики, ≤0,5 м при контакте с предметом; RTT 100 мс, jitter ±20 мс      |
| Сходимость остановленного контрольного ящика   | До 0,1 м за 500 мс после свежего состояния                                            |
| WebSocket-состояние                            | Среднее ≤30 КиБ/с на клиента за устойчивые 60 секунд при восьми участниках            |
| Обязательные ресурсы до первой игры            | ≤8 МиБ сжатых ресурсов; дальний фон измеряется отдельно                               |
| Стабильность                                   | По 30 минут spread и crowd, ограниченные очереди/кеши, отсутствие накопления ресурсов |

Фиксируйте версию кода/мира, оборудование и рендерер, качество/окно/масштаб, количество и типы предметов, число клиентов, прогрев и размер выборки. HTTP и WS учитываются отдельно. Телепортации не смешиваются с обычными коррекциями; пики не скрываются за квантилями. Сценарий 30× измеряется отдельно. Для серверного профиля браузеры и генераторы запускаются вне измеряемых 2 vCPU / 4 ГБ.

Машинные журналы, снимки и видео находятся в `output/`, исключённом из Git. Краткие отчёты сохраняются в `reports/`. Старый отчёт подтверждает свой прогон, а не автоматически каждый последующий коммит. Восемь участников не подтверждают поддержку 50.
