# Каталог моделей мира

Каталог описывает авторские модели для будущих инструментов поиска и редактирования мира.
Он включает модели без размещений и не определяет разрешённые игровые операции.
Геометрия и физика по-прежнему публикуются через manifest мира; действующая расстановка
хранится в PostgreSQL. Интерфейс каталога и превью относятся к следующему этапу.

## Источники истины

| Файл                                                          | Назначение                                                    |
| ------------------------------------------------------------- | ------------------------------------------------------------- |
| `content/buildings/**/asset.json`                             | Стабильный `assetId`, карточка `metadata`, источник геометрии |
| `content/buildings/**/source.json` или авторский GLB          | Геометрия, материалы и физическая форма                       |
| `content/buildings/**/catalog.json`                           | Регистрация `assetId → относительный путь дескриптора`        |
| `content/buildings/categories.json`                           | Общий справочник категорий всех миров                         |
| `dist/worlds/<worldId>/manifest.json`                         | Версии, bounds и пути ресурсов готовых моделей                |
| `dist/model-catalogs/<worldId>/index.json`                    | Указатель на текущую версию каталога                          |
| `dist/model-catalogs/<worldId>/catalog.<catalogVersion>.json` | Проверяемый неизменяемый снимок карточек и связей с ресурсами |

Метаданные редактируют только в дескрипторе. Производные файлы и списки количеств
в документации не служат вторым источником. Общий справочник категорий принадлежит
репозиторию: сборщик читает его относительно своего модуля, независимо от расположения
временного мира или текущего рабочего каталога. Общие контракты находятся в
`packages/contracts/src/world-model-catalog.ts`, файловые операции — в
`tools/world-build/src/model-catalog.ts`.

## Карточка модели

Формат дескриптора сохраняет `formatVersion: 1`; блок `metadata` обязателен для
каждой зарегистрированной модели, включая тестовые и основание:

```json
{
  "formatVersion": 1,
  "assetId": "tree-birch-small",
  "metadata": {
    "name": "Берёза, малый размер",
    "description": "Берёза со светлым стволом и гранёной зелёной кроной.",
    "category": "vegetation",
    "tags": ["birch", "small", "tree"]
  },
  "source": { "kind": "kit", "file": "source.json" }
}
```

- `name`: русское понятное название, 1–120 символов. Повторения допустимы; идентичность задаёт `assetId`.
- `description`: краткое описание внешности, назначения или особенностей, 1–1600 символов.
- `category`: один существующий ключ из общего справочника.
- `tags`: до 24 уникальных тегов; пустой массив допустим. Тег — до 40 символов, строчные латинские буквы, цифры и дефис, первый символ — буква или цифра.

Названия и описания должны быть непустыми, без крайних пробелов и управляющих символов.
Неизвестные поля внутри `metadata` отклоняются, чтобы опечатки не теряли данные.
Ключ категории — до 80 символов того же формата, что и `assetId`; её русское название — до 120 символов.

Категории: `buildings`, `vegetation`, `street-furniture`, `lighting`, `barriers`,
`playgrounds`, `landmarks`, `ground`. Узкие признаки выражайте тегами: `tree`,
`birch`, `small`, `school`, `arch`, `test`. Используйте существующее написание тегов.
Новая категория добавляется в общий справочник вместе с осмысленным названием.

Назначение и адрес реального здания указывайте только по подтверждённым сведениям,
например из `docs/ring-block.md`. Для неизвестного здания достаточно наблюдаемого
описания фасада и формы; не угадывайте адрес или функцию. Варианты стен и площадок
имеют названия для различения существующих форм, их номера не являются ID.
Размеры, bounds, коллайдеры, положение и поворот не копируют в дополнительные поля
карточки: они берутся из технических данных и экземпляров. При изменении внешнего
вида обновляйте название, описание и теги, если они перестали соответствовать модели.

## Производный индекс

`pnpm world:build` проверяет карточки до публикации мира и создаёт каталог отдельно
для `ring-block`, `physics-lab`, `streaming-lab`. Формат снимка:

```ts
type WorldModelCatalog = {
  formatVersion: 1;
  worldId: string;
  assetReleaseVersion: string;
  catalogVersion: string;
  categories: Record<string, { name: string }>;
  models: Record<
    string,
    {
      assetId: string;
      metadata: WorldModelMetadata;
      sourceKind: 'house' | 'footprint' | 'kit' | 'ground' | 'glb';
      runtimeAssetIds: string[];
    }
  >;
};
```

Ключ `models` совпадает с авторским `assetId`. Обычно `runtimeAssetIds` содержит
тот же единственный ID. У основания список содержит сгенерированные плитки;
у неиспользованного основания он может быть пустым. Сборщик записывает эту связь
при генерации, не восстанавливает её по похожим именам. Поэтому основание остаётся
одной карточкой, даже если в выпуске оно представлено 40 моделями.

Каждый runtime ID принадлежит ровно одной карточке и существует в manifest; все
модели manifest покрыты каталогом. Деревья представлены теми же ID, даже когда
используют процедурный профиль без GLB. Bounds, версия и ссылки на GLB/parts/коллизии
получаются соединением `runtimeAssetIds` с `manifest.assets` выбранного выпуска.
Каталог не назначает права и не делает основание или памятник автоматически
доступным для размещения: это будущая серверная политика инструмента.

`catalogVersion` — SHA-256 от UTF-8 `canonicalJson(worldModelCatalogIdentity(catalog))`,
где исключено только само поле `catalogVersion`. Порядок ключей канонизирован,
теги и ссылки на ресурсы отсортированы. Указатель `index.json` содержит
`formatVersion`, `worldId`, `assetReleaseVersion`, `catalogVersion` и заменяется
атомарно после записи снимка. Прежние снимки сохраняются; повторная сборка той же
версии сверяет байты. Повреждённый снимок под существующим хешем отклоняется.

Читатель сначала проверяет указатель, затем снимок, SHA-256, совпадение мира и
выпуска, категории и все ссылки на runtime-модели. CLI дополнительно сравнивает
карточки с текущими исходниками. Он не пересобирает геометрию: после правок рецепта
сначала выполните `pnpm world:build`.

Правка карточки или справочника меняет `catalogVersion`, сохраняя версии ресурсов,
`assetReleaseVersion`, `seedVersion`, `mapVersion` и физический хеш. Миграция БД для
такой правки не нужна. Снимок не входит в manifest и не копируется в публикации
расстановки `layouts/`; текущие URL этих публикаций сохраняют свою неизменяемость.
Каталог пока локальный артефакт: HTTP API, загрузка в клиенте и редактор не добавлены.

При программном `buildWorld(source, output)` каталог по умолчанию записывается в
`<output>/model-catalog/`, чтобы временные сборки оставались изолированными.
Третий аргумент задаёт явную папку; штатный CLI использует `dist/model-catalogs/<worldId>/`.

## Добавление и проверка

1. Создайте модель и заполните обязательный блок `metadata` в `asset.json`.
2. Зарегистрируйте её в подходящем `catalog.json`, сохранив стабильный ID.
3. Выполните `pnpm world:catalog:check --sources` — проверяются все карточки, ссылки на исходники и незарегистрированные дескрипторы. Эта проверка также входит в `pnpm check`.
4. Выполните `pnpm world:build`, затем `pnpm world:catalog:check` — проверяются снимки, контрольные суммы, привязка к выпуску и соответствие карточек исходникам.
5. Для изменения геометрии или состава моделей выполните обычную процедуру принятия выпуска из [памятки карты](map-model-guide.md). Для правки только метаданных шаг миграции не нужен.

Регрессии находятся в `packages/contracts/src/world-model-catalog.test.ts`,
`tests/integration/world-model-catalog.test.ts` и
`tests/integration/static-asset-library-preflight.test.ts`: неполные карточки,
категории и ссылки, модели без размещений, группировка плиток, воспроизводимость,
повреждение снимка и независимость геометрии/физики/публикаций расстановки от карточки.
