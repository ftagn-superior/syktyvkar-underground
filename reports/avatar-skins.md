## Результат

Ветка `personals` обновлена fast-forward до `feat/school-ring-district`
(`16ae331`, включая предметы и инвентарь). Предыдущие незакоммиченные
изменения персонажей восстановлены и конфликты совмещены.

Выделен общий `AvatarRig` с именованными суставами и общим применением
позы. Геометрия вынесена в фабрики `minifigure` и `standard`, которые
используют один `CharacterAnimator`. Скин не влияет на физику и скорость.

Каталог в `contracts` задаёт ID, подписи и совместимый каркас. Клиентская
таблица фабрик проверяется типами на полноту. В интерфейсе каталогу
соответствуют карточки с обычными радиокнопками и локальными SVG.
Для аккаунта выбор сохраняется вместе с именем и цветом; при нажатии
«Войти» изменённые настройки сначала сохраняются. Гость выбирает скин
до входа, предпочтение запоминается в пределах вкладки.

Миграция общей схемы БД v3 добавляет `player_profiles.skin_id` с
`minifigure` по умолчанию. БД проверяет формат ID, приложение — каталог.
Сервер читает внешний вид аккаунта из БД и реплицирует `skinId` всем
участникам. Клиент не может подменить его гостевым параметром входа.
Сетевой протокол обновлён до v5; формат мира v3 принят из ветки предметов.

## Перед запуском на существующей БД

Выполнить `pnpm db:migrate` (для собранного артефакта —
`pnpm db:migrate:built`), затем запускать клиент и сервер одной версии.
Прежние профили получат текущую минифигурку. Новые записи каталога
не требуют отдельной миграции перечисления скинов.

## Конфликт миграций после добавления предметов

Ошибка сохранения `Account request could not reach PostgreSQL` оказалась
ошибкой схемы: журнал PostgreSQL показывал отсутствие
`player_profiles.skin_id` (SQLSTATE `42703`). Соединение с БД работало,
кодировка сервера и клиента — UTF-8. В `su_schema_migrations` уже стояли
версии 1 и 2, но версия 2 была миграцией предметов из `78ecafe`,
а наша ранняя ветка скинов использовала тот же номер. Проверка версии
при запуске не могла различить эти две схемы.

Исправление: общий реестр `apps/server/src/migrations.ts`, миграция
скинов v3 и протокол v5 поверх протокола v4 предметов. Старый отдельный
реестр аккаунтов удалён согласно новой архитектуре. Существующие
имена, цвета, версии профилей, сессии и предметы сохраняются.
Для БД с ранней skin-only v2 предусмотрено добавление недостающей
схемы инвентаря в одной транзакции, выбранный скин не заменяется.
Повторный запуск безопасен. Ошибки HTTP аккаунтов теперь журналируют
SQLSTATE и имя ограничения без содержимого профилей и токенов.

Проверены переходы v1 → v3, inventory v2 → v3 и skin-only v2 → v3.
Сценарий inventory v2 проверяет неизменность строк предметов и
сохранение скина после обновления; skin-only v2 — неизменность профиля
и сессии и работоспособность предметов после обновления.

Перед обновлением локальной `syktyvkar_underground` создан полный
резервный дамп `/tmp/personals-before-schema-v3-16ae331.dump`, права 0600.
Миграция применена и повторена. Контрольные суммы всех прежних полей
строк в девяти таблицах аккаунтов и предметов совпали до и после;
исключено только новое поле `skin_id`. Запись скина через настоящий
`AccountStore.updateProfile` на существующем профиле успешно
проверена внутри транзакции с последующим ROLLBACK. Настройки
пользователя при этой проверке не менялись.

При проверке реального запуска также обнаружена несовместимость сохранения
карты из `objects` с объединённой геометрией (138 → 288 зданий). Хеш
сохранения точно совпадал с артефактом `objects`. Типы предметов и их
физические параметры не изменились. Для единственного сохранённого
ящика текущая поза и `safePose` прошли проверку `PhysicsWorld.checkPlacement`
в Havok на новой карте. Под той же advisory-блокировкой владельца мира
и в SQL-транзакции выполнен явный переход: изменён только
`persistent_worlds.compatibility_hash`, с проверкой точных прежнего и
нового хешей. Контрольные суммы остальных полей всех девяти таблиц
совпали; ящик, его положение и владельцы не менялись. Это отдельная
проверенная операция над этой локальной БД; автоматического принятия
произвольной новой геометрии в сервере нет.

Реальный городской сервер успешно запущен на локальной рабочей БД:
`/health/ready` — HTTP 200, `/api/world` — протокол 5, `/api/me` — HTTP 200.
Проверочный сервер штатно остановлен; идентификаторы, типы, свойства,
местонахождение и версии размещения прежних предметов сохранены.
Собранная поставка готова к обычному запуску через `make run`.
